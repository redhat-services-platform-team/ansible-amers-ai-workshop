= Module 2 lab assets: Python to Ansible

Migrate the NetBox installer that has accumulated fifty fictional maintainers, contradictory handovers, and responsibility for keeping the company operational.
Read the code to determine what it actually does.

== Files

* `legacy/install_netbox.py` is copied from `~/netbox-python/install_netbox.py`. Workshop comments add the maintainer story; executable behavior is unchanged.
* `legacy/.env.example` is copied unchanged from the same directory. Secret values are blank.
* `prompt.md` is the canonical migration prompt shared with Module 3.
* `starter/inventory.ini.example` names the `netbox_lab` group and contains a documentation-only host address.
* `migration-checklist.adoc` maps installer behavior to review criteria.
* `facilitator-guide.adoc` covers delivery and optional deployment validation.
* `output/` contains learner projects and is ignored by Git.

Follow `documentation/modules/ROOT/pages/02-shell-to-ansible.adoc` for the learner instructions.
The existing `02-shell-to-ansible` directory and page names are retained so workshop links keep working.
The exercise now migrates Python rather than the previous shell-script example.

Declare additional collection dependencies in `requirements.yml` when needed.
Module 3 uses `run-a/`, `run-b/`, and `run-c/` under the same learner directory.
Keep the canonical prompt and both input files identical across model comparisons.
Only the output destination changes.

== Control host and managed host

Use your existing Ansible installation on your RHEL or macOS control workstation for generation and syntax checks.
The installer explicitly supports a dedicated CentOS Stream 10 managed host.
Do not run the installer on your workstation or an existing shared server.
It installs packages, changes PostgreSQL and Nginx configuration, starts services, and may open firewall ports.

The base exercise requires no live target.
An optional deployment needs a disposable CentOS Stream 10 VM, SSH access, sudo, and network access to release archives and package sources.
Use separate fresh VMs or restore the same clean snapshot before testing each model.
Do not run the Python installer and generated Ansible project on the same dirty baseline for a fair comparison.

== Secrets and version state

The script stores its selected release and generated credentials in `/etc/netbox-installer/state.json` on the managed host.
It retains the first resolved release, rejects changes to saved secrets, and refuses an unmanaged `/opt/netbox`.
The migration must account for these behaviors.
The original uses permissive lab defaults such as wildcard allowed hosts and HTTP; review them explicitly.
Real secrets belong in approved secret storage or an encrypted Ansible Vault file outside committed examples.
