= Lab: Comparing models and effort

[abstract]
Repeat the NetBox migration with fixed inputs. Try different models and reasoning effort levels, then compare the output, review work, time, and reported usage.

== Learning objectives

* Select models and reasoning effort settings in your tool.
* Change one setting at a time and record what changed in the output.
* Check which installer behaviors each output implements.
* Use your results to decide when to change models or increase effort.

== Before you start

Complete xref:02-shell-to-ansible.adoc[Lab 2: Python-to-Ansible NetBox migration].
Use the same tool and Ansible environment for all runs.
The shared inputs are under `workshop-content/02-shell-to-ansible/`:

* `legacy/install_netbox.py`
* `legacy/.env.example`
* `migration-checklist.adoc`
* `prompt.md`

Lab 2 started with your own prompt. This lab uses the supplied `prompt.md` unchanged so the initial request stays the same across runs.
Only the output directory changes.
Keep prior generated projects and conversations out of each run's context.
Use `workshop-content/03-managing-ai-costs/lab-scorecard.adoc` or your own notebook.

Generate and review locally during the comparison. Do not run the installer or deploy the generated projects during these runs.
Syntax checks do not prove that NetBox deploys correctly or that reruns preserve credentials.

== Step 1: Find the controls

In Codex, use the model picker or `/model` in the CLI to choose a model and a supported reasoning effort.
Start with Luna for the baseline. GPT-6.1 Sol is an option for the model comparison if your account has access.
See the link:https://learn.chatgpt.com/docs/models[official OpenAI model documentation] for current controls and availability.

In Cursor, select Composer for the baseline, then choose another approved model for comparison.
For the effort comparison, choose a model with reasoning effort settings in your client.
If a model has no effort selector, record `not exposed`. Choose another approved model for runs B and C.
See link:https://cursor.com/docs/models[Cursor's model documentation] and the options shown in your client.

Record the exact model name or version, reasoning effort label, interaction mode, and any speed setting.
A speed setting such as Fast is a separate control from reasoning effort.
Avoid automatic model routing for this experiment if you can select a model directly.
Record any model substitutions required by your account.

== Step 2: Plan the comparison

Choose at least two models and two supported effort levels on one model.
Use this plan when both models offer the same effort labels:

[cols="1,2,2,3",options="header"]
|===
| Run | Model | Reasoning effort | Question
| A | Composer or Luna | Record the baseline setting | What does the baseline produce?
| B | Another approved model | Same effort label as A, if supported | What changes when I change the model?
| C | Same model as B | A higher supported effort than B | What changes when I increase effort?
|===

For Cursor with no Composer effort selector, record A as `not exposed`.
Use two explicit effort levels on the model chosen for B and C.
Runs A and B then differ in both model and reasoning behavior.
The same effort label on different models may use different amounts of computation and cost.
Between B and C, only effort changes.

Keep the tool, interaction mode, permissions, source files, initial prompt, and review criteria the same.
Use a fresh conversation and separate output directory for each run:

[source,text]
----
workshop-content/02-shell-to-ansible/output/<your-name>/run-a/
workshop-content/02-shell-to-ansible/output/<your-name>/run-b/
workshop-content/02-shell-to-ansible/output/<your-name>/run-c/
----

If no available model offers two effort levels, complete the model comparison and record that limitation. Changing interaction mode does not compare reasoning effort.

== Step 3: Run the migrations

Repeat these steps for A, B, and C:

. Start a fresh conversation and set the planned model and effort. Confirm the settings before sending the prompt.
. Attach the installer, `.env.example`, and migration checklist.
. Paste the supplied `prompt.md` unchanged. In a separate sentence, name this run's output directory.
. Start a timer and review the generated project against the checklist.
. Save the first response before requesting corrections. Record missing behavior, assumptions, and file structure.
. Request corrections for issues you can identify. Save each follow-up so you can explain how the conversation changed.
. Stop when the output meets the definition of done in `prompt.md` or after 15 user turns, whichever comes first. Keep incomplete output and record what remains.
. Record total generation and review time, user turns, manual edits, and your review decision.

Count the initial prompt and each follow-up as user turns.
Follow-ups may differ because the outputs have different problems. Compare both the initial output and the final reviewed result.
Use these results to choose settings for this migration. Other tasks may produce different results.

If the project includes `requirements.yml`, review it and install the declared collections from its output directory:

[source,bash]
----
# Install the collections declared by this generated project.
ansible-galaxy collection install -r requirements.yml
----

Use its README for non-secret validation variables. Adjust paths for its layout:

[source,bash]
----
# Check syntax without connecting to the placeholder inventory host.
ansible-playbook -i inventory.ini.example --syntax-check site.yml
----

Record the errors and any fixes. If the project cannot reach syntax validation, record why.

== Step 4: Compare evidence

Use the same migration checklist for each output.
Check saved secrets and release state, database setup, service handlers, TLS behavior, and verification tasks.
Check that the code implements the behavior described in its README.

Answer in your notes:

* Which first output covered the source behavior most closely? What code supports that judgment?
* What changed between B and C when effort increased?
* Which output needed fewer corrections or less manual editing?
* Did higher effort improve the output enough to justify extra time or usage?
* What remains untested in each project?

=== Check AI costs in Harness

Use the Harness link and sign-in method supplied for the workshop.
Your instructor must have connected the AI billing source and granted access to its cost view.

. Open *Cloud & AI Cost Management* and select the workshop view in *Cost Explorer*. In the classic interface, select the workshop *Perspective*.
. Set the date range to cover your runs. Record the report's time zone and latest data timestamp.
. Apply the assigned account, project, or team filters that the view exposes. Confirm the report covers your usage.
. Group AI spend by *Model* or *Provider*. Record the displayed cost, currency, and filters in your scorecard.
. Use session or request details only if the workshop has trace attribution. Otherwise, record costs for the report's available period and scope.

Provider billing totals do not identify individual runs or reasoning effort settings.
If several runs share a model or account, do not assign the whole total to one run.
Record `unavailable` when the report cannot isolate a run or has not ingested its usage yet.
Recheck later and record when you checked.
See link:https://developer.harness.io/docs/cloud-cost-management/cost-explorer/[Harness Cost Explorer] and link:https://developer.harness.io/docs/cloud-cost-management/ai-cost-management/overview/[AI cost attribution].

If your tool's usage is not connected to Harness, use its account report.
Cursor users can check link:https://cursor.com/dashboard/spending[Spending]. Codex users can use the usage view or their organization's report.
Elapsed time and turn counts cannot tell you what a run cost.

You may repeat a run to see whether the same settings produce similar results.
Record repeats separately so you can compare how much the results vary.

== Step 5: Decide what you would use next

Write a few rules based on your results.
Name a task where you would keep Composer or Luna, a task where you would try another model, and a reason to increase effort.
Explain each choice with an example from your runs.

== Completion checklist

* You compared at least two approved models with the same initial prompt and source files.
* You compared two supported effort levels on one model, or documented why access prevented that comparison.
* You saved separate outputs and recorded the actual settings and follow-ups.
* You reviewed behavior coverage and recorded syntax results, missing work, and untested runtime behavior.
* You can explain which settings you would use for the team project and why.
