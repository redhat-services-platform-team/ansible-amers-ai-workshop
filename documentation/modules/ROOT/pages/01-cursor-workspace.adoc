= Lab: Cursor Workspace Setup

[abstract]
Request Cursor access, install Cursor, point Dev Containers at *Podman*, and open this lab inside the community Ansible Development Tools (ADT) container.

== Learning Objectives

After completing this module, you will be able to:

* Request and obtain Cursor access for Red Hat associate use
* Install Cursor and the Anysphere Dev Containers extension
* Point Cursor Dev Containers at Podman (`dockerPath` and related settings)
* Reopen the Lab 1 workspace inside the Ansible Development Tools container via Podman
* Run a sample playbook from the Dev Container terminal in Cursor
* Apply basic best practices for AI-assisted Ansible development

== Prerequisites

Before you start this lab, complete the following on your local machine:

.Prerequisites
====
* *Podman* installed and working on your workstation (Podman Desktop is recommended on macOS and Windows)
* On macOS or Windows: a Podman *machine* created and *running*
* On Linux: the user Podman API socket enabled (`systemctl --user enable --now podman.socket`)
* Ability to install desktop software (Cursor) and receive email at your Red Hat address
====

.Verify Podman before you continue
====
In a host terminal:

[source,sh]
----
podman version
podman info
podman run --rm quay.io/podman/hello
podman container ls --all --format json
----

* `podman info` must succeed.
* On macOS/Windows, `podman machine list` should show the default machine as *running*.
* JSON listing may be an empty list `[]`; broken or non-JSON output will break Dev Containers later.

Optional — pre-pull the ADT image so the first Dev Container open is faster:

[source,sh]
----
podman pull {ansible_dev_tools_image}
----
====

[NOTE]
====
This lab does *not* walk through installing or configuring Podman.
If Podman is not installed, use link:https://podman-desktop.io/[Podman Desktop,window=_blank] (or your platform package manager) and return here when the checks above succeed.
====

== 1: Overview

link:https://cursor.com[Cursor,window=_blank] is an AI-enhanced code editor built on a VS Code–compatible foundation.
It integrates chat, inline edit, and agent workflows so you can write, explain, and refactor automation content with natural language while still reviewing every change like a normal pull request.

At Red Hat, Cursor is an approved AI development tool for associate use (subject to local laws and Works Council availability).
Access is request-based, usage is consumption-based, and models available *inside* Cursor are covered under Red Hat's contract when Red Hat guidelines are followed.

This lab gets you from *no Cursor install* to a verified workspace running *inside* the community Ansible Development Tools container.
The workshop standard is **Podman** as the container engine that Cursor Dev Containers uses to start that image.

Associated lab assets (including `.devcontainer/` and `.vscode/settings.json`) are in `workshop-content/01-cursor-workspace/`.

[NOTE]
====
This lab is designed for your local machine; Red Hat Demo Platform Showroom hosts workshop documentation—it is not a substitute for installing Cursor.
====

== 4: Point Cursor Dev Containers at Podman

Cursor's Dev Containers feature is provided by the *Anysphere* extension (`anysphere.remote-containers`).
By default it looks for `docker`.
You must change the executable path to `podman` and ensure Podman is reachable when Cursor starts.

=== 4.1 Install the Dev Containers extension

.Procedure
====
. In Cursor, open *Extensions* (`Ctrl+Shift+X` / `Cmd+Shift+X`).
. Search for *Dev Containers* published by *Anysphere*.
. Install *Dev Containers* (`anysphere.remote-containers`).
+
image::01-cursor-workspace/cursor-dev-containers-extension.png[Extensions view showing Dev Containers by Anysphere with Install button,width=720]
. Reload Cursor if prompted.
. Confirm the Command Palette shows *Dev Containers:* commands (for example *Dev Containers: Reopen in Container*).
====

=== 4.2 Set Docker Path to Podman (required)

Do this in *User* settings so it applies before and after opening a Dev Container.
The Lab 1 folder also ships `.vscode/settings.json` with the same values for workspace scope.

.Procedure
====
. Open the Command Palette → *Preferences: Open User Settings (JSON)*.
. Add (or merge) these settings:
+
[source,json]
----
{
  "dev.containers.dockerPath": "podman",
  "dev.containers.dockerComposePath": "podman-compose"
}
----
+
image::01-cursor-workspace/cursor-docker-path-settings.png[User settings.json with dev.containers.dockerPath set to podman,width=720]
. Save the file.
. Fully quit and restart Cursor so the extension picks up the new path.
====

.Verification
====
* In *Settings* UI, search for `docker path` and confirm it shows `podman`.
+
image::01-cursor-workspace/cursor-docker-path-settings-ui.png[Settings UI showing Dev Containers Docker Path set to podman,width=720]
* From a terminal on the host, `which podman` returns an executable Cursor can find on its `PATH`.
====

[TIP]
====
If Cursor was started from a GUI launcher and cannot find `podman`, launch Cursor once from a terminal where `podman` works (so it inherits your shell `PATH`), or put Podman on the system PATH used by GUI apps.
====

=== 4.3 Optional: expose Podman via DOCKER_HOST

Some tooling expects a Docker-style host URL.
Point `DOCKER_HOST` at the Podman socket, then restart Cursor from that same environment.

*macOS*::
+
[source,sh]
----
export DOCKER_HOST="unix://$(podman machine inspect --format '{{.ConnectionInfo.PodmanSocket.Path}}')"
echo "$DOCKER_HOST"
# Start Cursor from this shell if the GUI app does not see Podman:
# open -a Cursor
----

*Linux*::
+
[source,sh]
----
export DOCKER_HOST="unix://${XDG_RUNTIME_DIR}/podman/podman.sock"
echo "$DOCKER_HOST"
----

*Windows (PowerShell)*::
+
[source,powershell]
----
podman machine inspect --format '{{.ConnectionInfo.PodmanPipe.Path}}'
# Example DOCKER_HOST form: npipe:////./pipe/podman-machine-default
----

Persist `DOCKER_HOST` in your shell profile if you use it regularly.
Podman Desktop can also show connection details under machine settings.

=== 4.4 Optional: install Ansible extensions locally

These are also installed *inside* the Dev Container via `devcontainer.json`:

* *Ansible* (`redhat.ansible`)
* *YAML* (`redhat.vscode-yaml`)

== 6: Reopen Lab 1 in the ADT Dev Container (via Podman)

.Before you click Reopen
====
* Podman machine is *running* (macOS/Windows) or `podman.socket` is active (Linux)
* `podman info` succeeds in a host terminal
* Cursor User settings set `dev.containers.dockerPath` to `podman`
* You opened `workshop-content/01-cursor-workspace` (not the repo root)
====

.Procedure
====
. Wait for Cursor to detect the Dev Container config, or open the Command Palette.
. Run *Dev Containers: Reopen in Container*.
+
image::01-cursor-workspace/cursor-reopen-in-container.png[Command Palette with Dev Containers Reopen in Container selected,width=720]
. Watch the Dev Containers log if shown.
Cursor should invoke *podman* (not docker) to pull/start `{ansible_dev_tools_image}`.
. Wait for:
+
--
* Image pull (first time only, if not pre-pulled)
* Container create/start with the Lab 1 `runArgs` (capabilities, `/dev/fuse`, `userns=host`, and related options required for the ADT image under Podman)
* Extension install inside the container
* `postCreateCommand` printing `ansible-playbook` / `ansible-lint` versions
--
. Confirm the status bar shows a Dev Container connection (for example *Dev Container: ansible-dev-tools*).
. Open *Terminal → New Terminal*.
This shell is *inside* the ADT container managed by Podman.
====

.Expected tools in the container terminal
====
[source,sh]
----
ansible-playbook --version
ansible-lint --version
----
====

=== Inspect what Podman created (host check)

In a *host* terminal:

[source,sh]
----
podman ps --format "{{.ID}} {{.Names}} {{.Image}}"
----

You should see a running container based on `community-ansible-dev-tools`.

=== Rebuild after config or image changes

* *Dev Containers: Rebuild Container* — recreate after editing `devcontainer.json` or pulling a newer ADT tag
* *Dev Containers: Rebuild and Reopen in Container* — rebuild and reconnect
* *Dev Containers: Reopen Folder Locally* — leave the container and return to the host workspace

[source,sh]
----
podman pull {ansible_dev_tools_image}
----

Then rebuild the Dev Container so it is not stuck on an old layer.

== 8: Basic Best Practices for AI-Assisted Ansible Work

.Treat AI output as a draft
====
* Always read diffs before accepting changes.
* Prefer small, reviewable edits over large unreviewed agent rewrites.
* Run playbooks and linters *inside the Dev Container*.
====

.Protect secrets and proprietary data
====
* Do not paste passwords, tokens, customer data, or private keys into prompts.
* Prefer Privacy Mode / organization policy settings when available.
* Keep credentials in environment variables, Ansible Vault, or your platform secret store—not in chat history.
====

.Stay inside approved tooling boundaries
====
* At Red Hat, models available *inside* Cursor are covered under the existing contract for code generation when Red Hat guidelines are followed.
* Using those model providers *outside* Cursor is generally *not* covered by the same agreement and may need separate approval.
* Follow Red Hat AI use guidelines and any team-specific rules for customer engagements.
====

.Work with intentional context
====
* Point Cursor at specific files (`@filename`) instead of dumping entire repositories into every prompt.
* State goals, constraints (idempotent Ansible, no hard-coded secrets), and verification steps in your prompt.
* Prefer the Dev Container terminal so validation uses the shared ADT toolchain.
====

.Keep a reproducible runtime
====
* Keep Podman as the default engine for this workshop's Dev Containers.
* Commit workshop content to git before sharing or rebuilding docs (Antora indexes committed files when using the local content source).
====

== 10: Troubleshooting Podman + Cursor Dev Containers

[cols="1,2"]
|===
| Symptom | What to try

| Dev Containers still calls `docker` / cannot find Docker
| Set User `dev.containers.dockerPath` to `podman`, restart Cursor completely, confirm `which podman` works in a terminal Cursor inherits

| `podman machine` not running
| `podman machine start` or start the machine in Podman Desktop

| Permission / socket errors on Linux
| `systemctl --user enable --now podman.socket`; set `DOCKER_HOST=unix://$XDG_RUNTIME_DIR/podman/podman.sock`

| JSON / "Unexpected end of JSON input" when listing containers
| Run `podman container ls --all --format json` on the host; upgrade Podman/Podman Desktop; ensure the machine is running

| Container starts then Ansible/nested tooling fails with `mknod` / OCI permission errors
| Confirm you are using the Lab 1 default `.devcontainer/devcontainer.json` (includes `CAP_MKNOD`, `SYS_ADMIN`, `/dev/fuse`, `userns=host`, and related `runArgs`)

| GUI-launched Cursor cannot find `podman`
| Launch Cursor from a shell where `podman` is on `PATH`, or fix PATH for GUI applications

| Need a temporary Docker-only fallback
| See <<docker-fallback>>
|===

Use *Dev Containers: Show Log* from the Command Palette while reproducing failures—the log shows whether Cursor invoked `podman` or `docker`.

[#docker-fallback]
=== Docker fallback (not the workshop default)

If Podman cannot be made to work on your laptop during the session, a Docker-oriented config is available at `.devcontainer/docker/devcontainer.json`.
That path is a *contingency only*; facilitators should still help you complete the Podman setup when possible.
