= Lab: Python-to-Ansible NetBox migration

[abstract]
Write your own prompt to start migrating the Python NetBox installer. Try follow-up requests, explore the tools, and inspect what they produce.

== The handover

Fifty maintainers have touched the installer over several years.
The runbook is missing, the wiki disagrees with the comments, and everyone agrees that this script holds the company together.
Your assignment is to replace it with automation the next maintainer can review and operate.

The maintainer history is workshop fiction.
We copied the installer from `netbox-python` and added comments. Its executable code is unchanged.
Read the code to determine what the installer does.

== Learning objectives

* Write a prompt in your own words and give the tool relevant files.
* Try follow-up requests and see how they change the response.
* Review generated changes and use Ansible validation when you have runnable output.
* Record what helped, what confused you, and what you want to try next.

== Before you start

Complete xref:01-cursor-workspace.adoc[Module 1: Workspace setup].
Use Codex or Cursor and your existing Ansible environment on the RHEL or macOS control workstation.
Choose an approved model available in your tool.
You can change prompts, models, or interaction modes as you experiment.
A partial migration is a useful result if you can explain what you tried and what remains.
You do not need to finish a full NetBox deployment in this lab.

Run terminal commands from the repository root unless a step changes directories.

[source,bash]
----
ansible-playbook --version
----

Generate and review the projects locally for the base exercise.
Deployment validation is a separate optional step on a disposable CentOS Stream 10 VM.
The installer requires root and changes system configuration. Do not execute it on your control workstation.

== Step 1: Read the inherited installer

Open both inputs:

* `workshop-content/02-shell-to-ansible/legacy/install_netbox.py`
* `workshop-content/02-shell-to-ansible/legacy/.env.example`

Start with `main()` and follow a few of its function calls.
Notice the packages, database, services, and saved state it manages.
You can ask the tool to explain unfamiliar code after you write your first prompt.
Use the code to check its answer and the claims in the maintainer comments.

The migration checklist is available at `workshop-content/02-shell-to-ansible/migration-checklist.adoc` when you want a closer review.
You do not need to understand every installer stage before starting.

== Step 2: Prepare a place for your work

Replace `learner` with your name without spaces:

[source,bash]
----
lab_output=workshop-content/02-shell-to-ansible/output/learner
mkdir -p "$lab_output/attempt-1"
cp workshop-content/02-shell-to-ansible/starter/inventory.ini.example "$lab_output/attempt-1/"
----

The starter inventory names the `netbox_lab` group and uses a documentation-only IP address.
Leave it as an example during generation and syntax review.
Git ignores learner output.
Save your first prompt and a few notes in this folder so you can compare them with later attempts.

== Step 3: Write your own first prompt

Before opening `prompt.md`, write a request in your own words.
You might ask for a migration plan, an explanation followed by a small conversion, or an initial Ansible project.
Choose a starting point that you can review.

Think about what the tool needs to know:

* What do you want it to do with the installer?
* Which source files should it read?
* Where should it save generated files?
* What should it explain so you can review the result?

Include the local output directory and tell the tool to generate or explain code without executing the installer or deploying it.
Keep real credentials out of the conversation.
The control workstation runs Ansible; the installer targets a dedicated CentOS Stream 10 host.

. Start a conversation in Codex or Cursor and select your model.
. Attach the installer and `.env.example`, or give their repository paths to the agent.
. Send your own prompt and read the response before accepting changes.
. Save the prompt and note what the tool understood, what it assumed, and what you would change.

There is no required wording or single correct prompt.
If the answer misses your intent, use that to decide your next request.

== Step 4: Experiment with follow-up requests

Try something that answers a question you have about the tool or output.
For example, ask it to explain a generated task, convert one installer stage, revise a variable name, or check whether secrets survive a second run.
Inspect the diff after each change.

You can also try a fresh conversation, another approved model, or a different interaction mode.
If you want to preserve the first attempt, create another folder:

[source,bash]
----
mkdir -p "$lab_output/attempt-2"
cp workshop-content/02-shell-to-ansible/starter/inventory.ini.example "$lab_output/attempt-2/"
----

Tell the tool to save the new attempt there.
Changing one thing at a time can help you see its effect, but you are free to explore.
Record prompt and mode changes so you can explain the differences you see.

=== Optional prompt resource

After trying your own prompt, you can read `workshop-content/02-shell-to-ansible/prompt.md`.
It is a detailed example, not the required starting prompt for this lab.
Borrow useful requirements, edit it, or try it in a separate conversation to compare the response.
You can also ask the tool to suggest improvements to your original prompt.
Note which suggestions you choose and why.

The example asks for a full migration, which may take longer than a focused experiment.
Use as much of it as helps your current task.

== Step 5: Review and validate what you have

Look at the files the tool created and compare them with the installer.
Use the migration checklist as a reference when needed.
Ask the tool to explain anything you cannot follow, then check the explanation against the code.
Pay attention to target hosts, saved secrets, release selection, and tasks that always restart services.
Record missing behavior rather than assuming the output is complete.

If your attempt has `site.yml` and `inventory.ini.example`, check syntax from that project directory:

[source,bash]
----
(
  cd "$lab_output/attempt-1"
  ansible-playbook -i inventory.ini.example --syntax-check site.yml
)
----

Adjust the paths if the tool used a different layout.
If the project declares collection dependencies, review `requirements.yml` and install them in your existing Ansible environment before retrying:

[source,bash]
----
(
  cd "$lab_output/attempt-1"
  ansible-galaxy collection install -r requirements.yml
)
----

Run the collection command only if that file exists.
Follow the generated README for non-secret variable files needed by validation.
Read any error before asking for a correction, and compare the next result with the previous one.

If you only generated a plan or a partial conversion, record that instead of trying to validate a missing project.
Syntax checking does not prove a deployment works or that a second run preserves credentials and release state.
Keep runtime behavior marked as untested until you test it on a disposable target.

== Step 6: Reflect on the experiment

Save brief notes alongside your prompts and generated files:

* What did your first prompt produce?
* Which follow-up or tool setting changed the result?
* What did you accept, edit, or reject after reading the output?
* What remains incomplete or untested?
* What would you try next?

You can use the Module 2 rows in `workshop-content/03-managing-ai-costs/lab-scorecard.adoc` or your own notebook.
Record the actual model, tool and mode, and whether you used your own prompt, an edited example, or the supplied prompt.
Leave the optional experiment row blank if you only made one attempt.
Differences here can come from your prompts, context, model, or mode. They are observations to discuss, not a controlled model ranking.

== Step 7: Optional deployment validation

Use a disposable, dedicated CentOS Stream 10 VM with SSH access and sudo.
Your facilitator must supply or confirm the target before this step.
Replace the example address and user in a separate `inventory.ini`, following the generated README.
Review the complete project before running it.
Use the generated project's documented variables and secret storage.

. Start each attempt from a fresh VM or restore the same clean snapshot before comparing deployments.
. Deploy using the project's README. Confirm the enabled and active PostgreSQL, Valkey, NetBox, NetBox worker, and Nginx services.
. Check the login page through Nginx and verify the configured admin account without recording credentials.
. Run again with identical inputs. Investigate every repeated change, migration, and restart.
. Confirm the selected release and saved credentials did not change. Do not print secrets into the scorecard.
. Test optional TLS and firewall behavior separately if time permits. Record which branches you actually tested.

A first check-mode pass may lack packages, files, or databases required by later tasks.
Read the project's check-mode limitations before interpreting the result.
On a second run, check whether repeated work is needed or simply carried over from the script.

== Completion checklist

* You wrote and sent your own first prompt.
* You tried a follow-up request or another change and inspected its effect.
* You saved the prompts, output, and notes about what you learned.
* You recorded validation results or explained why the output was not ready for validation.
* You identified a question or improvement to explore next.

An unfinished migration can satisfy this lab.
The goal is to get familiar with the tools and learn how to guide and review their output.
