= Lab: Python-to-Ansible NetBox migration

[abstract]
Migrate the Python NetBox installer into an Ansible project with two AI models. Review each result for missing behavior and problems on a second run.

== The handover

Fifty maintainers have touched the installer over several years.
The runbook is missing, the wiki disagrees with the comments, and everyone agrees that this script holds the company together.
Your assignment is to replace it with automation the next maintainer can review and operate.

The maintainer history is workshop fiction.
We copied the installer from `netbox-python` and added comments. Its executable code is unchanged.
Read the code to determine what the installer does.

== Learning objectives

* Trace the installer's execution order, dependencies, and saved state.
* Use AI to build an Ansible project with modules, templates, and handlers.
* Check how the migration handles credentials, release selection, second runs, and target requirements.
* Compare two generated projects using the same inputs and validation rules.

== Before you start

Complete xref:01-cursor-workspace.adoc[Module 1: Workspace setup].
Use Codex or Cursor and your existing Ansible environment on the RHEL or macOS control workstation.
Your facilitator will name two approved models, Model A and Model B.
Keep the tool and interaction mode constant across both runs.

Run terminal commands from the repository root unless a step changes directories.

[source,bash]
----
ansible-playbook --version
----

Generate and review the projects locally for the base exercise.
Deployment validation is a separate optional step on a disposable CentOS Stream 10 VM.
The installer requires root and changes system configuration. Do not execute it on your control workstation.

== Step 1: Read the inherited installer

Open both inputs:

* `workshop-content/02-shell-to-ansible/legacy/install_netbox.py`
* `workshop-content/02-shell-to-ansible/legacy/.env.example`

Trace `main()` and the functions it calls.
Use `workshop-content/02-shell-to-ansible/migration-checklist.adoc` to record what each stage changes.

[cols="1,2",options="header"]
|===
| Stage | Questions to answer before generation
| Inputs and validation | Which defaults, environment overrides, and validation rules affect the install?
| State | Where are secrets and the chosen release stored? What happens on the next run?
| Packages and database | What must exist before PostgreSQL and Valkey can serve NetBox?
| Application | How are the release, service user, config, migrations, and admin account created?
| Services and web access | Which systemd units, Nginx files, TLS options, SELinux rules, and firewall ports are managed?
| Verification | What does the readiness probe prove, and what does it leave untested?
|===

Write down two rerun risks and one security limitation you found in the code.
For example, service restarts occur unconditionally, and the local HTTPS probe does not verify certificate trust.
Use the code to check the claims in the comments.

== Step 2: Create separate project directories

Replace `learner` with your name without spaces:

[source,bash]
----
lab_output=workshop-content/02-shell-to-ansible/output/learner
mkdir -p "$lab_output/model-a" "$lab_output/model-b"
cp workshop-content/02-shell-to-ansible/starter/inventory.ini.example "$lab_output/model-a/"
cp workshop-content/02-shell-to-ansible/starter/inventory.ini.example "$lab_output/model-b/"
----

The starter inventory uses the `netbox_lab` group and a documentation-only IP address.
Leave it as an example during generation and syntax review.
Learner output is ignored by Git.

== Step 3: Generate with Model A

. Start a new conversation and select Model A.
. Attach both legacy inputs or tell the agent to read their exact paths. Use the same migration checklist for both models.
. Paste `workshop-content/02-shell-to-ansible/prompt.md` unchanged. Add an instruction naming your `model-a/` output directory.
. Start a timer and check how the plan accounts for each installer stage.
. Let it generate the project, then inspect the diff before accepting it.

The project should include `site.yml`, non-secret variable examples, an example inventory, and a README.
Use task or role files and templates where needed.
A wrapper that simply executes `install_netbox.py` does not complete the migration.

Check the following:

* The play targets `netbox_lab`, with privilege escalation on the managed host.
* The project implements every installer stage or lists what is missing.
* Generated secrets survive reruns and stay out of logs and example files.
* The project keeps the saved release and rejects an unmanaged install.
* Handlers reload or restart services when required. The README explains any commands that could not use a module.
* The README explains inputs, dependencies, execution, and what remains untested.

Count every follow-up prompt and manual correction as rework.
Do not ask the agent to deploy while generating the project.

== Step 4: Validate the project locally

In a subshell, enter Model A's project so relative role, template, and variable paths resolve correctly:

[source,bash]
----
(
  cd "$lab_output/model-a"
  ansible-playbook -i inventory.ini.example --syntax-check site.yml
)
----

If the project declares collection dependencies, review `requirements.yml` and install them in your existing Ansible environment before retrying:

[source,bash]
----
(
  cd "$lab_output/model-a"
  ansible-galaxy collection install -r requirements.yml
)
----

Run that command only when the generated project includes `requirements.yml`.
If syntax validation needs variable files, follow the generated README and use non-secret examples.
Record missing dependencies or configuration requirements.

Syntax checking does not contact the target, install NetBox, prove credentials are stable, or establish idempotency.
Use the migration checklist to review the implementation and mark runtime checks as untested.
Read the source's validation rules and compare them with the generated assertions.
Request corrections for missing behavior even if the syntax check passes.

== Step 5: Repeat with Model B

. Start a new conversation with Model B. Do not include Model A's project or conversation.
. Supply the same two legacy inputs, migration checklist, and unchanged canonical prompt.
. Change only the destination instruction to your `model-b/` directory.
. Review the plan, generated project, and behavior coverage using the same criteria.
. Run the syntax check from Model B's project directory and record the same evidence.

[source,bash]
----
(
  cd "$lab_output/model-b"
  ansible-playbook -i inventory.ini.example --syntax-check site.yml
)
----

== Step 6: Compare the migrations

[source,bash]
----
diff -ru "$lab_output/model-a" "$lab_output/model-b"
----

`diff` exits with code 1 when the projects differ.
Compare what the projects do and how much work they need before you would accept them.

[cols="1,2",options="header"]
|===
| Criterion | Evidence
| Coverage | The project implements each stage, including TLS, SELinux, and readiness checks, or lists what is missing
| State and secrets | The project reuses credentials and the selected release, protects files and logs, and rejects unmanaged installs
| Second runs | Modules, handlers, and command guards prevent unnecessary work; the README explains restrictions on concurrent runs
| Instructions | The inventory, variables, dependencies, validation commands, and deployment steps are clear
| Verification | Record syntax results, review findings, and runtime checks completed or left untested
| Rework | Follow-up prompts, manual edits, unresolved gaps, and elapsed time
|===

Fill the existing Module 2 Model A and Model B rows in `workshop-content/03-managing-ai-costs/lab-scorecard.adoc` or a notebook copy.
Record actual model names, tool and mode, elapsed minutes, and user turns including the initial prompt.
Use `merge` for an accepted result without manual edits, `edit` for a result you corrected, and `discard` for an unsuitable result.
Record deployment testing separately from this review decision.
Write one sentence explaining your preference and the largest remaining risk.

== Step 7: Optional deployment validation

Use a disposable, dedicated CentOS Stream 10 VM with SSH access and sudo.
Your facilitator must supply or confirm the target before this step.
Replace the example address and user in a separate `inventory.ini`, following the generated README.
Review the complete project before running it.
Use the generated project's documented variables and secret storage.

. Start each model from a separate fresh VM or the same restored clean snapshot.
. Deploy using the project's README. Confirm the enabled and active PostgreSQL, Valkey, NetBox, NetBox worker, and Nginx services.
. Check the login page through Nginx and verify the configured admin account without recording credentials.
. Run again with identical inputs. Investigate every repeated change, migration, and restart.
. Confirm the selected release and saved credentials did not change. Do not print secrets into the scorecard.
. Test optional TLS and firewall behavior separately if time permits. Record which branches you actually tested.

A first check-mode pass may lack packages, files, or databases required by later tasks.
Read the project's check-mode limitations before interpreting the result.
On a second run, check whether repeated work is needed or simply carried over from the script.

== Completion checklist

* You saved both projects and their reports in separate directories.
* Syntax checks pass, or the scorecard explains rejected or incomplete results.
* You reviewed persistent state, secrets, release selection, and all installer stages.
* The scorecard distinguishes static review from any runtime validation.
* You recorded a preferred result and remaining gaps.
