= Lab: Customer NetBox delivery project

[abstract]
Work as a delivery team for a fictional company. Migrate the inherited Python installer to Ansible and deploy NetBox infrastructure in your AWS environment. Manually add demo hosts to NetBox and query them with Ansible's dynamic inventory plugin.

== The customer

Switchboard Supply has depended on the Lab 2 installer for years.
The people named in its comments have moved teams, the deployment instructions are incomplete, and nobody wants to be the next person to run it by hand.
The company also manages AWS networks and keeps copying host addresses into static inventories.

Your team has been asked to make the deployment repeatable and show how Ansible can use NetBox as a source of inventory.
The customer wants working automation, evidence that it survives a second run, and instructions another team can follow.
Use `workshop-content/04-aws-lab-provisioning/customer-brief.adoc` as your project brief.

This is an open-ended collaboration. Choose your architecture, division of work, prompts, models, and project layout.
Agree on a scope your team can deliver. Explain any tradeoffs or unfinished work to the customer.
There is no required team size or competition score.

== Deliverables

* Reviewed Ansible content that installs and configures NetBox and its dependencies, based on the Python installer from Lab 2.
* Running AWS hosts for the NetBox infrastructure, with a documented network layout and deployment procedure.
* Manually created NetBox host records and a working demo that queries them through `netbox.netbox.nb_inventory`.
* A customer handover with validation evidence, operating instructions, known limitations, and cleanup steps.

The final demo must execute an Ansible play against team-owned AWS hosts selected from NetBox.
Show the host records in NetBox and the inventory returned by the plugin.

== Before you start

Complete Labs 1 through 3.
Bring your own AWS environment that your team is authorized to use for testing and deployment.
Confirm the account, region, allowed services, IAM permissions, budget, and cleanup owner together.
Use your existing RHEL or macOS Ansible control workstation and an approved AI tool.

You need access to EC2 and the networking resources your design requires.
Use the community NetBox installation based on the Lab 2 script.
Your team will enter its demo hosts in the NetBox UI after deployment.

== Step 1: Organize the team

Create a team branch and a project directory. Replace `switchboard` with your team name:

[source,bash]
----
# Create a branch for the team's delivery work.
git switch -c team/switchboard-netbox
# Create a directory for the project and its customer handover.
mkdir -p workshop-content/04-aws-lab-provisioning/teams/switchboard
----

Agree on shared variables and file ownership before parallel work.
Divide responsibilities such as the installer migration, AWS infrastructure, NetBox host records, inventory demo, and review.
Pair or rotate roles so everyone can explain at least one part of the delivery.
Ask a teammate or another team to act as the customer during scope review and the final demo.
Review each other's changes and resolve conflicting assumptions in the code and README.

Bring forward useful work from Labs 2 and 3.
Choose the port you want to continue, or start a new one if the review evidence supports that decision.
Use your model comparison notes to decide which requests need more reasoning effort.
Write your own prompts; this lab provides a customer brief rather than a prescribed conversation.

== Step 2: Agree on an architecture and acceptance plan

Sketch the AWS hosts, subnets, access paths, and NetBox services.
Decide whether to keep the installer's services on one host or split application, PostgreSQL, and Valkey roles.
Choose a supported OS and compatible dependency versions. If you change the source's OS assumptions, document and test those changes.

[TIP]
====
Start by considering `t3.small` instances for lightweight demo targets or separated low-load components.
They have 2 vCPUs and 2 GiB of memory. That is not a sizing guarantee for a complete NetBox stack.
For an all-in-one community NetBox host, consider a larger instance such as `t3.medium` and measure memory during installation and the demo.
Check regional availability, CPU credit behavior, storage, and current costs before launching.
See link:https://docs.aws.amazon.com/ec2/latest/instancetypes/gp.html[AWS instance specifications].
====

Use instance roles or your organization's approved temporary credentials.
Restrict administrative access to the team's approved network or access service.
Keep PostgreSQL and Valkey private. Choose appropriate HTTPS and certificate handling for the customer-facing endpoint.
Tag team resources so you can identify ownership and clean them up without affecting shared infrastructure.

Choose how to create the AWS hosts. Ansible provisioning is encouraged; existing approved infrastructure is acceptable if you document it.
Use Ansible for the NetBox installation and configuration.
Define the deployment entry point and a separate bootstrap inventory so you can deploy NetBox before its inventory API is available.

Write acceptance checks before generating more code.
Include fresh installation, a second run, saved credentials, release persistence, HTTP or HTTPS access, service health, manually entered host records, dynamic inventory, and cleanup.

== Step 3: Finish the Ansible migration

Use the source installer and `workshop-content/02-shell-to-ansible/migration-checklist.adoc` to account for its behavior.
A wrapper that runs the original Python installer is not a completed migration.

Use roles or task files with clear responsibilities, fully qualified module names, variable defaults, templates, and handlers.
Declare collection dependencies and supported versions.
Use shell or command tasks only where a suitable module is unavailable; document their change detection and rerun behavior.
Protect secrets with approved secret storage or Ansible Vault, restrictive file permissions, and `no_log` where required.
Keep secrets out of prompts, committed examples, and demo evidence.

Preserve generated secrets and the selected release across reruns.
Explain any intentional changes to the installer's state file, refusal conditions, wildcard allowed-hosts default, TLS behavior, or unconditional restarts.
Define what the playbook supports for upgrades and recovery. Do not claim production readiness from a workshop deployment.

Read the generated changes before running them.
Run syntax checks and your available lint tools, then deploy to the agreed AWS hosts.
Save service, login, and API verification results.
Run the deployment again and investigate changes that should not repeat. Document necessary exceptions, such as explicit migration tasks.

== Step 4: Manually add demo hosts to NetBox

Choose team-owned AWS hosts for the inventory demo.
Use their actual names and addresses. Confirm how your control workstation will reach them.

Add the records through the NetBox UI:

. Create any supporting records your chosen host type requires, such as a site or cluster.
. Create a virtual-machine or device record for each demo host and set its status to active.
. Add an interface to each host.
. Create an IP address with its prefix length and assign it to that host's interface.
. Set the address as the host's primary IPv4 or IPv6 address.
. Add the same team-specific tag to each demo host so your inventory can select them.

Check each host's name, primary IP, status, and tag in NetBox before querying the inventory.
Document these manual steps in the customer handover so another operator can add a host.

== Step 5: Query the NetBox dynamic inventory

Use `netbox.netbox.nb_inventory` for the final inventory source.
Read its link:https://docs.ansible.com/projects/ansible/latest/collections/netbox/netbox/nb_inventory_inventory.html[inventory plugin documentation] and install the required collection and Python dependencies.
Keep the API endpoint and token in your environment or approved credential store.
Use a read-only inventory token for the queries.
Keep certificate validation enabled and document any private CA trust configuration.
Filter the inventory to the team's demo tag and hosts with primary addresses.
Choose addresses reachable from your control workstation, or configure an approved connection path.

Document the inventory filename, group selection, connection user, and credentials required for the demo.
You may use AWS discovery or a static inventory to bootstrap NetBox; the final customer demo must read host selection from NetBox.

Adapt these commands to your project from its directory:

[source,bash]
----
# Query NetBox and display only the groups selected by your inventory configuration.
ansible-inventory -i inventory/netbox.yml --graph
# Test Ansible connectivity to hosts selected from NetBox, not a static host list.
ansible netbox_demo -i inventory/netbox.yml -m ansible.builtin.ping
# Run the team's demo playbook against the same NetBox inventory.
ansible-playbook -i inventory/netbox.yml demo.yml
----

These filenames and `netbox_demo` group are a suggested interface, not supplied working files.
Your team implements and documents them.

Change a demo host's tag or another inventory filter field in NetBox, refresh the inventory, and show that host selection changes without editing a static host list.
Restore the record afterward. Account for inventory caching in your refresh procedure.

== Step 6: Present the customer demo

Present the original problem and explain what the customer can now do with Ansible.
Use `workshop-content/04-aws-lab-provisioning/customer-demo-checklist.adoc` to prepare evidence.

Demonstrate the deployed NetBox service and explain the Ansible content that configured it.
Show a second deployment run and describe any remaining changes.
Show the hosts your team manually entered in NetBox, including their interfaces, primary IPs, and team tag.
Query the NetBox inventory and run your demo playbook against the selected AWS hosts.
Show the inventory membership change and explain how the customer would add another host in NetBox.

Describe what you tested, what remains incomplete, and what would need more work before production use.
Give the customer a README with setup, dependency versions, required permissions, deployment, rerun, verification, manual host entry, dynamic inventory, recovery, and teardown instructions.
Include your architecture decisions and useful AI model comparison findings.

== Step 7: Handover and cleanup

Review the staged files for credentials and private output before committing your team's work.
Agree on how to share the branch or pull request with the customer.
Keep the source, sanitized evidence, and operating instructions together.

Use your documented teardown process after the demo, unless the environment owner explicitly wants the resources retained.
Remove only team-owned resources. Account for instances, volumes, public addresses, and network resources.
Verify the result in AWS and record any retained resources, their owner, and expiry.

== Completion checklist

* The team has reviewed Ansible content that installs and configures NetBox.
* NetBox infrastructure is running on the team's AWS hosts, with installation and rerun evidence.
* The team manually added demo host records, interfaces, primary addresses, and a team tag in NetBox.
* The customer demo queries NetBox dynamic inventory and runs Ansible against the selected AWS hosts.
* Inventory membership changes when the team changes a NetBox record.
* The handover explains limitations, operating procedures, and cleanup, with no committed secrets.
