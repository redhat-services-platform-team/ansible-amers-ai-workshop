Lab: Managing AI costs

Use the NetBox installer from Module 2 for a fixed-prompt comparison of three models. Compare usage, time, and corrections, then write rules for your own work.

Learning objectives

  • Identify the account, model, tokens, and interaction mode that affect usage.

  • Compare three models using the same migration prompt and inputs.

  • Record the work needed to accept each output.

  • Choose practical rules for controlling usage.

Before you start

Complete Module 2: Python-to-Ansible NetBox migration or read its installer and example inputs. The shared files are under workshop-content/02-shell-to-ansible/:

  • legacy/install_netbox.py

  • legacy/.env.example

  • migration-checklist.adoc

  • prompt.md

Use workshop-content/03-managing-ai-costs/lab-scorecard.adoc or a notebook copy to record results. Facilitators can use facilitator-talk-track.md and deck-slide-outline.md in that directory. Slide references below match the outline.

Keep Spending open during the lab. If it is unavailable, record elapsed time and turns, and use your enterprise usage report if available. These measurements alone do not establish spend.

Module 2 encouraged your own prompts and experiments. Here, use the supplied prompt.md unchanged and hold the input files constant across runs.

The timed runs cover generation and static review. Keep optional VM deployment checks separate from this timing. Do not run the installer or deploy generated projects during these runs. Record untested runtime behavior and missing implementation details.

Step 1: Record your billing context

Facilitator slides 3 and 4 cover billing and usage pools.

  1. Open Spending or your enterprise usage report.

  2. Record the billing period reset date and the pool names shown in your account.

  3. Record the selected model, interaction mode, and any router mode shown in the tool.

  4. Add these details to the scorecard or your notebook.

Step 2: Review usage patterns

Facilitator slide 9 covers usage patterns. Allow two minutes.

Write one example from Module 2, the workshop, or your work for each pattern:

  • A narrow request that names one change and the relevant files.

  • Repeated requests to fix an output that still fails review or validation.

  • A long agent session with many tool calls.

Step 3: Prepare three migration runs

Facilitator slides 5, 6, 10, and 11 cover models, inputs, and recording results.

Migrate the same Python NetBox installer three times. Use a new conversation for each run and keep the prompt and input files unchanged.

  1. Create output directories under your learner folder:

    workshop-content/02-shell-to-ansible/output/<your-name>/run-a/
workshop-content/02-shell-to-ansible/output/<your-name>/run-b/
workshop-content/02-shell-to-ansible/output/<your-name>/run-c/

  2. Keep the canonical prompt.md ready to copy for each run.

  3. Choose the models your facilitator assigns. Use a cost-efficient model for Run A, a balanced model for Run B, and an approved escalation model for Run C.

If no escalation model is available, repeat B using Agent and record the mode change. Changing the mode means the comparison includes that difference as well as model choice.

Step 4: Run A

  1. Start a new conversation and select the Run A model.

  2. Attach the legacy installer, .env.example, and migration checklist. Keep prior generated projects out of the conversation.

  3. Paste prompt.md unchanged and name your run-a/ output directory.

  4. Review the generated project against the checklist.

  5. Follow its README for collection dependencies and non-secret variable files. From the generated project directory, run ansible-playbook -i inventory.ini.example --syntax-check site.yml.

  6. Stop when the definition of done in prompt.md is met or you reach 15 user turns, whichever comes first. Record any missing behavior at the limit.

  7. Fill the Run A scorecard row with the actual model, tool and mode, elapsed minutes, user turns, review decision, and corrections.

  8. Check Spending. If exact usage is unavailable, you may record a subjective low, medium, or high estimate in Notes.

Count the initial prompt and every follow-up as user turns. A syntax pass does not prove that NetBox deploys correctly or that a second run leaves credentials and release state unchanged.

Step 5: Run B

  1. Start a new conversation and select Run B’s model.

  2. Use the same attachments and unchanged prompt. Save the project under run-b/.

  3. Review coverage and check syntax using the same steps and stopping rule as Run A.

  4. Fill the Run B scorecard row.

Step 6: Run C

  1. Start a new conversation and select Run C’s model or assigned mode.

  2. Use the same attachments and unchanged prompt. Save the project under run-c/.

  3. Review coverage and check syntax using the same steps and stopping rule as Run A.

  4. Fill the Run C scorecard row.

Step 7: Compare the results

Facilitator slides 2, 12, and 13 cover the Module 2 comparison and review costs.

Compare Runs A, B, and C using their fixed inputs. You can also discuss your Module 2 notes, but those attempts may have different prompts, context, or modes. Their time and results are not a controlled comparison with these runs. Answer in your scorecard notes or notebook:

  • Which accepted result needed the fewest user turns?

  • Which run would you choose under a monthly usage limit, and why?

  • Did a more expensive model reduce corrections or missing behavior?

Include manual review and edits when comparing the work needed to accept a result. Mark incomplete or discarded outputs so they are not counted as successful migrations.

Step 8: Write personal rules

Facilitator slide 12 covers personal rules.

Write three sentences in the scorecard’s Personal rules section. Choose actions you can apply to your work, such as trying a cheaper model before escalating, attaching only relevant inputs, or reading validation errors before requesting a correction.

Step 9: Optional CLI comparison

Facilitator slide 7 covers interaction modes.

Repeat Run A with cursor-agent using the same prompt, legacy input files, and checklist. Record CLI mode and note any differences in turns or usage compared with the editor run.
