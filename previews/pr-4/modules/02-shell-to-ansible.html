Lab: Python-to-Ansible NetBox migration

Turn a company-critical Python NetBox installer into an Ansible project, then compare how two AI models handle its behavior and maintenance risks.

The handover

Fifty maintainers have touched the installer over several years. The runbook is missing, the wiki disagrees with the comments, and everyone agrees that this script holds the company together. Your assignment is to replace it with automation the next maintainer can review and operate.

The maintainer history is workshop fiction. The installation code is a real Python installer copied from netbox-python; only comments were added. Treat the code as the source of truth.

Learning objectives

  • Read a procedural installer and map its dependencies and persistent state.

  • Use AI to build an Ansible project with modules, templates, and handlers.

  • Review credentials, release selection, rerun behavior, and host assumptions.

  • Compare two generated projects using the same inputs and validation rules.

Before you start

Complete Module 1: Workspace Setup. Use Codex or Cursor and your existing Ansible environment on the RHEL or macOS control workstation. Your facilitator will name two approved models, Model A and Model B. Keep the tool and interaction mode constant across both runs.

Run terminal commands from the repository root unless a step changes directories.

ansible-playbook --version

The base exercise generates and reviews code without connecting to a managed host. Deployment validation is a separate optional step on a disposable CentOS Stream 10 VM. The source installer requires root and changes system configuration; do not execute it on your control workstation.

Step 1: Read the inherited installer

Open both inputs:

  • workshop-content/02-shell-to-ansible/legacy/install_netbox.py

  • workshop-content/02-shell-to-ansible/legacy/.env.example

Trace main() and the functions it calls. Use workshop-content/02-shell-to-ansible/migration-checklist.adoc to record what each stage changes.

Stage Questions to answer before generation

Inputs and validation

Which defaults, environment overrides, and validation rules affect the install?

State

Where are secrets and the chosen release stored? What happens on the next run?

Packages and database

What must exist before PostgreSQL and Valkey can serve NetBox?

Application

How are the release, service user, config, migrations, and admin account created?

Services and web access

Which systemd units, Nginx files, TLS options, SELinux rules, and firewall ports are managed?

Verification

What does the readiness probe prove, and what does it leave untested?

Write down two rerun risks and one security limitation you found in the code. For example, service restarts occur unconditionally, and the local HTTPS probe does not verify certificate trust. Identify facts from the code separately from jokes in comments.

Step 2: Create separate project directories

Replace learner with your name without spaces:

lab_output=workshop-content/02-shell-to-ansible/output/learner
mkdir -p "$lab_output/model-a" "$lab_output/model-b"
cp workshop-content/02-shell-to-ansible/starter/inventory.ini.example "$lab_output/model-a/"
cp workshop-content/02-shell-to-ansible/starter/inventory.ini.example "$lab_output/model-b/"

The starter inventory uses the netbox_lab group and a documentation-only IP address. Leave it as an example during generation and syntax review. Learner output is ignored by Git.

Step 3: Generate with Model A

  1. Start a new conversation and select Model A.

  2. Attach both legacy inputs or tell the agent to read their exact paths. Include the migration checklist as the common review criteria for both models.

  3. Paste workshop-content/02-shell-to-ansible/prompt.md unchanged. Add an instruction naming your model-a/ output directory.

  4. Start a timer and review the model’s behavior map and plan.

  5. Let it generate the project, then inspect the diff before accepting it.

The project should include site.yml, task or role files, templates as needed, non-secret variable examples, an example inventory, and a README. A wrapper that simply executes install_netbox.py does not complete the migration.

Review especially:

  • The play targets netbox_lab, with privilege escalation on the managed host.

  • Every installer stage has an implementation or an explicitly recorded gap.

  • Generated secrets survive reruns and stay out of logs and example files.

  • A saved release stays pinned; an unmanaged install is rejected.

  • Handlers control necessary reloads and restarts, with documented command exceptions.

  • The README explains input mapping, dependencies, execution, and untested behavior.

Count every follow-up prompt and manual correction as rework. Do not ask the agent to deploy while generating the project.

Step 4: Validate the project locally

In a subshell, enter Model A’s project so relative role, template, and variable paths resolve correctly:

(
  cd "$lab_output/model-a"
  ansible-playbook -i inventory.ini.example --syntax-check site.yml
)

If the project declares collection dependencies, review requirements.yml and install them in your existing Ansible environment before retrying:

(
  cd "$lab_output/model-a"
  ansible-galaxy collection install -r requirements.yml
)

Run that command only when the generated project includes requirements.yml. If syntax validation needs variable files, follow the generated README and use non-secret examples. Record missing dependencies or configuration requirements.

Syntax checking does not contact the target, install NetBox, prove credentials are stable, or establish idempotency. Use the migration checklist to review the implementation and mark runtime checks as untested. Read the source’s validation rules and compare them with the generated assertions. Request focused corrections for missing behavior instead of accepting a successful syntax check as completion.

Step 5: Repeat with Model B

  1. Start a new conversation with Model B. Do not include Model A’s project or conversation.

  2. Supply the same two legacy inputs, migration checklist, and unchanged canonical prompt.

  3. Change only the destination instruction to your model-b/ directory.

  4. Review the plan, generated project, and behavior coverage using the same criteria.

  5. Run the syntax check from Model B’s project directory and record the same evidence.

(
  cd "$lab_output/model-b"
  ansible-playbook -i inventory.ini.example --syntax-check site.yml
)

Step 6: Compare the migrations

diff -ru "$lab_output/model-a" "$lab_output/model-b"

diff exits with code 1 when the projects differ. Compare behavior and maintainability, rather than file count alone.

Criterion Evidence

Coverage

Every installer stage is accounted for, including TLS, SELinux, and readiness

State and secrets

Credential persistence, protected files/logs, release pinning, unmanaged-install refusal

Rerun design

Module choices, handlers, guarded migrations and commands, concurrent-run policy

Operability

Clear inventory, input mapping, dependencies, validation and deployment instructions

Verification

Syntax result, review findings, runtime evidence or explicit untested status

Rework

Follow-up prompts, manual edits, unresolved gaps, and elapsed time

Fill the existing Module 2 Model A and Model B rows in workshop-content/03-managing-ai-costs/lab-scorecard.adoc or a notebook copy. Record actual model names, tool and mode, elapsed minutes, and user turns including the initial prompt. Use merge for an accepted result without manual edits, edit for a result you corrected, and discard for an unsuitable result. These labels describe your review decision, not a verified production deployment. Write one sentence explaining your preference and the most significant remaining risk.

Step 7: Optional deployment validation

Use a disposable, dedicated CentOS Stream 10 VM with SSH access and sudo. Your facilitator must supply or confirm the target before this step. Replace the example address and user in a separate inventory.ini, following the generated README. Review the complete project before running it. Use the generated project’s documented variables and secret storage.

  1. Start each model from a separate fresh VM or the same restored clean snapshot.

  2. Deploy using the project’s README. Confirm the enabled and active PostgreSQL, Valkey, NetBox, NetBox worker, and Nginx services.

  3. Check the login page through Nginx and verify the configured admin account without recording credentials.

  4. Run again with identical inputs. Investigate every repeated change, migration, and restart.

  5. Confirm the selected release and credential state stayed stable. Do not print secrets into the scorecard.

  6. Test optional TLS and firewall behavior separately if time permits. Record which branches you actually tested.

A first check-mode pass may lack packages, files, or databases required by later tasks. Review documented check-mode limitations instead of treating check mode as an isolated deployment test. For a repeated install, distinguish necessary reconciliation from unconditional work inherited from the script.

Completion checklist

  • Both model projects and their coverage reports are saved separately.

  • Syntax checks pass, or the scorecard explains rejected or incomplete results.

  • You reviewed persistent state, secrets, release selection, and all installer stages.

  • The scorecard distinguishes static review from any runtime validation.

  • You recorded a preferred result and remaining gaps.

Proceed to Module 3: Managing AI Costs, which reuses these inputs and the same prompt for its cost comparison.
