Lab: Python-to-Ansible NetBox migration

Write your own prompt and make one initial port of the Python NetBox installer with Composer in Cursor or Luna in Codex. Use follow-up requests to learn how to guide and review the tool.

The handover

Fifty maintainers have touched the installer over several years. The runbook is missing, the wiki disagrees with the comments, and everyone agrees that this script holds the company together. Your assignment is to replace it with automation the next maintainer can review and operate.

The maintainer history is workshop fiction. We copied the installer from netbox-python and added comments. Its executable code is unchanged. Read the code to determine what the installer does.

Learning objectives

  • Write a prompt in your own words and give the tool relevant files.

  • Try follow-up requests and see how they change the response.

  • Review generated changes and use Ansible validation when you have runnable output.

  • Record what helped, what confused you, and what you want to try next.

Before you start

Complete Module 1: Workspace setup. Use Codex or Cursor and your existing Ansible environment on the RHEL or macOS control workstation. Select Composer if you use Cursor, or Luna if you use Codex. Use the Composer version available to your account, or gpt-6-luna in Codex. For Luna, start with High reasoning effort if available. Record the actual model and setting. Keep that model throughout this lab and work on one port in attempt-1/. If your account lacks the requested model, use an approved available model and note the substitution. Lab 3 is where you will compare models and effort levels. See the Composer documentation and official OpenAI model documentation for available controls. A partial migration is a useful result if you can explain what you tried and what remains. You do not need to finish a full NetBox deployment in this lab.

Run terminal commands from the repository root unless a step changes directories.

# Check the Ansible installation on your control workstation.
ansible-playbook --version

Generate and review your port locally for this exercise. The installer requires root and changes system configuration. Do not execute it on your control workstation.

Step 1: Read the inherited installer

Open both inputs:

  • workshop-content/02-shell-to-ansible/legacy/install_netbox.py

  • workshop-content/02-shell-to-ansible/legacy/.env.example

Start with main() and follow a few of its function calls. Notice the packages, database, services, and saved state it manages. You can ask the tool to explain unfamiliar code after you write your first prompt. Use the code to check its answer and the claims in the maintainer comments.

The migration checklist is available at workshop-content/02-shell-to-ansible/migration-checklist.adoc when you want a closer review. You do not need to understand every installer stage before starting.

Step 2: Prepare a place for your work

Replace learner with your name without spaces:

# Set the folder for your prompts, notes, and generated project.
lab_output=workshop-content/02-shell-to-ansible/output/learner
# Create the directory for this lab's single port.
mkdir -p "$lab_output/attempt-1"
# Copy the placeholder inventory for local syntax checks.
cp workshop-content/02-shell-to-ansible/starter/inventory.ini.example "$lab_output/attempt-1/"

The starter inventory names the netbox_lab group and uses a documentation-only IP address. Leave it as an example during generation and syntax review. Git ignores learner output. Save your first prompt and a few notes in this folder so you can refer to them in Lab 3.

Step 3: Write your own first prompt

Before opening prompt.md, write a request in your own words. You might ask for a migration plan, an explanation followed by a small conversion, or an initial Ansible project. Choose a starting point that you can review.

Think about what the tool needs to know:

  • What do you want it to do with the installer?

  • Which source files should it read?

  • Where should it save generated files?

  • What should it explain so you can review the result?

Include the local output directory and tell the tool to generate or explain code without executing the installer or deploying it. Keep real credentials out of the conversation. The control workstation runs Ansible; the installer targets a dedicated CentOS Stream 10 host.

  1. Start a conversation in Codex or Cursor and select your model.

  2. Attach the installer and .env.example, or give their repository paths to the agent.

  3. Send your own prompt and read the response before accepting changes.

  4. Save the prompt and note what the tool understood, what it assumed, and what you would change.

There is no required wording or single correct prompt. If the answer misses your intent, use that to decide your next request.

Step 4: Experiment with follow-up requests

Try something that answers a question you have about the tool or output. For example, ask it to explain a generated task, convert one installer stage, revise a variable name, or check whether secrets survive a second run. Inspect the diff after each change.

Continue improving the same port with your selected model. Keep notes about each follow-up and inspect its changes before asking for more. You can change the request as you learn, but save model and effort comparisons for Lab 3.

Optional prompt resource

After trying your own prompt, you can read workshop-content/02-shell-to-ansible/prompt.md. It is a detailed example, not the required starting prompt for this lab. Borrow useful requirements or edit it to guide a follow-up on the same port. You can also ask the tool to suggest improvements to your original prompt. Note which suggestions you choose and why.

The example asks for a full migration, which may take longer than a focused experiment. Use as much of it as helps your current task.

Step 5: Review and validate what you have

Look at the files the tool created and compare them with the installer. Use the migration checklist as a reference when needed. Ask the tool to explain anything you cannot follow, then check the explanation against the code. Pay attention to target hosts, saved secrets, release selection, and tasks that always restart services. Record missing behavior rather than assuming the output is complete.

If your attempt has site.yml and inventory.ini.example, check syntax from that project directory:

(
  # Enter the generated project directory.
  cd "$lab_output/attempt-1"
  # Check playbook syntax without connecting to the example host.
  ansible-playbook -i inventory.ini.example --syntax-check site.yml
)

Adjust the paths if the tool used a different layout. If the project declares collection dependencies, review requirements.yml and install them in your existing Ansible environment before retrying:

(
  # Enter the generated project directory.
  cd "$lab_output/attempt-1"
  # Install the collections declared by this project.
  ansible-galaxy collection install -r requirements.yml
)

Run the collection command only if that file exists. Follow the generated README for non-secret variable files needed by validation. Read any error before asking for a correction, and compare the next result with the previous one.

If you only generated a plan or a partial conversion, record that instead of trying to validate a missing project. Syntax checking does not prove a deployment works or that a second run preserves credentials and release state. Record which behavior you checked and what remains untested.

Step 6: Reflect on the experiment

Save brief notes alongside your prompts and generated files:

  • What did your first prompt produce?

  • Which follow-up or tool setting changed the result?

  • What did you accept, edit, or reject after reading the output?

  • What remains incomplete or untested?

  • What would you try next?

You can use the Lab 2 row in workshop-content/03-managing-ai-costs/lab-scorecard.adoc or your own notebook. Record the actual model, effort setting, tool and mode, and which parts of the optional prompt you used. These notes describe one port and your follow-ups. Lab 3 uses fresh conversations for a controlled comparison.

Completion checklist

  • You wrote and sent your own first prompt.

  • You tried a follow-up request or another change and inspected its effect.

  • You saved the prompts, output, and notes about what you learned.

  • You recorded validation results or explained why the output was not ready for validation.

  • You identified a question or improvement to explore next.

An unfinished migration can satisfy this lab. The goal is to get familiar with the tools and learn how to guide and review their output.

Proceed to Module 3: Comparing models and effort. That lab uses the supplied prompt.md unchanged across runs to compare models and effort levels with fixed inputs. Your experiments here are useful discussion notes, but their prompts and settings may differ from that comparison.
