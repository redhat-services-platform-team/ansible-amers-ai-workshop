Lab 01: Workspace setup

Install Codex or Cursor on RHEL or macOS, sign in, and check your existing Ansible installation. Choose either CLI or desktop.

Learning objectives

  • Verify your existing Ansible installation is accessible to the selected AI tool

  • Install one AI tool: Codex or Cursor, using either its CLI or desktop interface

  • Authenticate the selected tool with your approved enterprise account

  • Open the workshop repository and verify the local Ansible runtime

  • Inspect the selected tool’s permissions and review AI-generated changes

Prerequisites

  • A RHEL or macOS workstation

  • A working Ansible installation, with ansible-playbook on your command path

  • Git and the download utilities required by your chosen installer

  • A graphical desktop session only if you choose a desktop interface; either CLI works from a terminal

  • Permission to install OS packages and outbound HTTPS access to the download services

  • On RHEL: registration and enabled package repositories

  • If choosing the macOS Homebrew installer: a working Homebrew installation

  • If choosing Codex: an enterprise Codex entitlement and membership in the assigned workspace

  • If choosing Cursor: an account approved for the workshop

Use your existing Ansible installation. If it requires a Python environment, activate that environment in each terminal used for the labs. Install Ansible before starting if it is not available. The lint check is optional.

Editing configuration files is optional

Install your chosen tool, sign in, and open the workshop repository to start working. The lab works without editing configuration files. Use the permissions examples and CLI options below when you want to change a setting. You can skip the configuration examples and continue to host runtime verification.

1: Verify Ansible

In the terminal you normally use for Ansible, activate your existing environment if needed, then run:

# Locate the Ansible executable in this terminal's environment.
command -v ansible-playbook
# Show the Ansible version, configuration path, and Python runtime.
ansible-playbook --version
# Confirm Git is available and show its version.
git --version

Check that all three commands succeed. Note the executable path and Python runtime shown by ansible-playbook --version. Your AI tool needs access to that installation. If Ansible is missing or fails to start, fix the installation before continuing.

2: Clone the workshop

Clone once; if you already have the checkout, change to its repository root instead:

# Download the workshop repository into a new local directory.
git clone https://github.com/redhat-services-platform-team/ansible-amers-ai-workshop.git
# Enter the cloned workshop repository.
cd ansible-amers-ai-workshop

Keep your existing Ansible environment available in the terminal used to launch the CLI or run validation.

3: Set up Codex

Follow this section if you chose Codex. Install either CLI or desktop. For CLI on macOS, choose one installer.

Codex CLI on RHEL and macOS

On RHEL, install the download utilities and sandbox dependency with sudo dnf install -y curl tar gzip less bubblewrap. On macOS, use the existing download utilities. Run the standalone installer as your regular user:

# Download the Codex installer to a temporary file for inspection.
curl -fsSL https://chatgpt.com/codex/install.sh -o /tmp/codex-install.sh
# Read the installer before running it; press q to exit less.
less /tmp/codex-install.sh
# Run the inspected Codex installer as your regular user.
sh /tmp/codex-install.sh
# Add the installer directory to the command path for this terminal.
export PATH="$HOME/.local/bin:$PATH"
# Show the installed Codex CLI version.
codex --version
# List the commands and flags supported by this installed version.
codex --help

The installer configures your shell path. Open a new terminal afterward, or use the PATH command above in the current one. Run the installer again to update. See official CLI installation.

macOS Homebrew alternative

If you prefer Homebrew, choose it instead of the standalone CLI installer:

# Install Codex CLI through Homebrew.
brew install --cask codex
# Show the installed Codex CLI version.
codex --version

Update this installation with brew upgrade --cask codex.

Codex desktop on macOS

  1. Download the ChatGPT desktop app from the official download page.

  2. Install and launch it, complete enterprise OAuth/SSO sign-in, and select the assigned enterprise workspace.

  3. Choose Codex and open the workshop repository folder.

See the desktop app guide.

Open ChatGPT from the applications menu, or run chatgpt in a graphical desktop session. Sign in through enterprise OAuth/SSO and select the assigned workspace. See official Linux desktop support and RPM instructions. RHEL remains an unsupported preview target even if installation succeeds.

Enterprise sign-in for CLI users

From a terminal:

# Start Codex account sign-in in your browser.
codex login
# Check whether Codex is signed in.
codex login status

Choose Sign in with ChatGPT, use your work identity, complete enterprise OAuth/SSO, and select the assigned enterprise workspace. Confirm workspace selection during sign-in; codex login status reports the authentication method.

For a RHEL SSH session, use codex login --device-auth, open the printed link on your laptop, and complete the same enterprise sign-in. Device login must be enabled by the workspace administrator. If it is disabled, use the SSH callback forwarding flow in the authentication guide. Keep cached authentication credentials out of Git.

Permissions

You can keep the installed settings. Use these examples only if you want to change permissions.

Permissions control file writes, command network access, and approval requests. Check them with /permissions in the CLI or the control beneath the desktop composer. Codex can run commands allowed by the sandbox without asking each time. Your organization may restrict the available settings.

Optional configuration reference

This example allows workspace edits and sends requests for more access to you for review. Edit ~/.codex/config.toml on RHEL or macOS. If you set CODEX_HOME, edit config.toml there instead.

Read and back up an existing file before editing it. Merge the example keys with your settings. Keep unrelated entries and avoid duplicate keys or table headers. For a new file, use the complete example below. Organization requirements take precedence over user defaults.

# Create the Codex settings directory if you choose to edit the examples.
mkdir -p "$HOME/.codex"
# Check for an existing config before making a backup.
if [ -f "$HOME/.codex/config.toml" ]; then
  # Save a timestamped copy of the existing Codex configuration.
  cp "$HOME/.codex/config.toml" "$HOME/.codex/config.toml.backup-$(date +%Y%m%d-%H%M%S)"
fi
# Open the configuration in your chosen editor, or vi if EDITOR is unset.
${EDITOR:-vi} "$HOME/.codex/config.toml"
approval_policy = "on-request"
approvals_reviewer = "user"
sandbox_mode = "workspace-write"

[sandbox_workspace_write]
network_access = false

Setting

What it means for a first-time user

approval_policy = "on-request"

Codex can perform routine actions inside its permissions. When it requests an action requiring more access, it can ask you to approve it; this does not prompt for every command.

approvals_reviewer = "user"

Approval requests go to you rather than an automatic reviewer, so you can read the proposed command and its purpose.

sandbox_mode = "workspace-write"

Generated commands can edit the workspace and run local validation. Writes outside the permitted roots are restricted; this is not a promise that reads are limited to the workspace.

network_access = false

Commands inside the workspace sandbox cannot freely contact remote services. This is separate from web search and does not block Codex’s own sign-in or model connection.

Place top-level keys before TOML table headers. If [sandbox_workspace_write] already exists, update network_access inside that table. If you edit the file, restart Codex and check the active permissions. The same sample is available at workshop-content/01-codex-workspace/samples/config.toml.

Optional CLI examples, using your existing Ansible installation. Choose one command for the session you want:

# Start a read-only session with approval requests for actions needing more access.
codex -s read-only -a on-request
# Allow workspace edits and ask for approval when more access is needed.
codex -s workspace-write -a on-request
# Start a session with the Lab 2 directory as its working directory.
codex -C workshop-content/02-shell-to-ansible
# Continue the most recent session for the current directory.
codex resume --last

If Ansible needs environment activation, tell Codex your actual activation command or give it the absolute executable path verified in section 1. The lab folder’s guide also covers named profiles, command rules, and administrator requirements.

4: Set up Cursor

Follow this section only if you chose Cursor. Install either CLI or desktop. Sign in with the account approved for the workshop. If your organization provides a license, complete its account setup before continuing.

CLI installation on RHEL and macOS

Run the installer as your regular user:

# Download the Cursor CLI installer to a temporary file for inspection.
curl -fsSL https://cursor.com/install -o /tmp/cursor-install.sh
# Read the installer before running it; press q to exit less.
less /tmp/cursor-install.sh
# Run the inspected Cursor CLI installer as your regular user.
bash /tmp/cursor-install.sh
# Add the installer directory to the command path for this terminal.
export PATH="$HOME/.local/bin:$PATH"
# Show the installed Cursor CLI version.
agent --version
# Start Cursor CLI account sign-in.
agent login
# Check the Cursor CLI authentication status.
agent status

Complete sign-in with the account approved for Cursor access. From the workshop repository root, use your existing Ansible environment and start an interactive session with agent. The CLI can update with agent update. See CLI installation and CLI sign-in.

If you chose CLI, skip the desktop installation steps below and continue to host runtime verification. The Permissions and References subsections are optional reading.

Desktop installation on RHEL

Download the Linux RPM for your architecture from Cursor downloads. Save it in ~/Downloads, then install the exact filename you downloaded:

# Enter the directory where you saved the downloaded RPM.
cd "$HOME/Downloads"
# Install the Cursor RPM after replacing the placeholder with its filename.
sudo dnf install './<downloaded-cursor-package>.rpm'

Replace <downloaded-cursor-package> with the actual filename. Launch Cursor from the applications menu and sign in with the account that received access. For repository-based installation and updates, see Cursor’s RHEL/Fedora setup.

Desktop installation on macOS

  1. Download the macOS installer for Apple Silicon or Intel from Cursor downloads.

  2. Open the .dmg, move Cursor into Applications, and launch it.

  3. Sign in with the account that received Cursor access.

Open the workspace in Cursor desktop

In Cursor, choose File → Open Folder… and select the repository root, ansible-amers-ai-workshop. Open Terminal → New Terminal, activate your existing Ansible environment if needed, and verify it is available:

# Locate the Ansible executable in this terminal's environment.
command -v ansible-playbook
# Show the Ansible version, configuration path, and Python runtime.
ansible-playbook --version

Use the same installation you verified in section 1. An optional Ansible extension published by Red Hat adds YAML editing and language support; terminal validation uses your installed Ansible tools.

Permissions

You can keep the installed settings. Use these examples only if you want to change permissions.

Cursor desktop and CLI use different settings. In desktop Cursor, open Settings → Agents → Approvals & Execution. For CLI, edit ~/.cursor/cli-config.json or the project file .cursor/cli.json. CLI settings do not change desktop Run Mode.

Optional configuration reference for desktop

Use Auto-review with sandboxing enabled. Allowlisted calls run immediately. Supported shell commands run in the sandbox; an automatic reviewer evaluates other calls. Some actions run without asking you. In Cursor 3.23 or later, choose Read Access → Workspace to require approval for reads outside the workspace unless they are allowlisted. Keep your organization’s restrictions.

To request review before publishing, installing software, or changing remote systems, merge this example into ~/.cursor/permissions.json for all projects or <repo>/.cursor/permissions.json for this workshop:

{
  "autoRun": {
    "allow_instructions": [],
    "block_instructions": [
      "Commands that publish code, including git push, should require my approval first.",
      "Commands that install software or change host configuration should require my approval first.",
      "Commands that connect to managed hosts or change AWS resources should require my approval first."
    ]
  }
}

allow_instructions adds no exceptions. block_instructions asks the reviewer to block the listed actions so the agent can ask for approval or try another approach. These instructions guide a model; they do not guarantee that a command will be blocked. Team policy can override local files. If your organization disables Auto-review, use Allowlist without adding automatic approvals.

Optional configuration reference for CLI

Inspect and back up ~/.cursor/cli-config.json, then merge these settings. The CLI may already have created this file when you signed in. If you use CURSOR_CONFIG_DIR or XDG_CONFIG_HOME, use the configured location instead. For a new file, this is a complete starting point:

{
  "version": 1,
  "editor": { "vimMode": false },
  "approvalMode": "allowlist",
  "permissions": {
    "allow": [],
    "deny": ["Shell(sudo)", "Shell(rm)"]
  }
}

Setting

What it means for a first-time user

version: 1

Selects the documented CLI configuration format.

editor.vimMode: false

Uses normal text-input keys; preserve your preference if you already use Vim bindings.

approvalMode: "allowlist"

Uses explicit permission rules rather than unrestricted execution or automatic review.

permissions.allow: []

Adds no blanket automatic approvals. Review approval requests before accepting them; existing sandbox behavior can still permit supported actions.

permissions.deny

Blocks commands whose base command is sudo or rm. These token rules do not block every possible way to change or remove files, and deny entries take precedence over allow entries.

Use an interactive agent session and read each command request. If a deny rule blocks an intended task, review it before running the command yourself or changing the rule.

Preserve existing settings before editing

Back up the files you plan to edit:

# Create the Cursor settings directory if you choose to edit the examples.
mkdir -p "$HOME/.cursor"
# Check whether a Cursor CLI config exists before backing it up.
if [ -f "$HOME/.cursor/cli-config.json" ]; then
  # Save a timestamped backup of the Cursor CLI configuration.
  cp "$HOME/.cursor/cli-config.json" "$HOME/.cursor/cli-config.json.backup-$(date +%Y%m%d-%H%M%S)"
fi
# Check whether desktop permission settings exist before backing them up.
if [ -f "$HOME/.cursor/permissions.json" ]; then
  # Save a timestamped backup of the Cursor desktop permission settings.
  cp "$HOME/.cursor/permissions.json" "$HOME/.cursor/permissions.json.backup-$(date +%Y%m%d-%H%M%S)"
fi

For project settings, back up the file in the repository’s .cursor/ directory. Merge keys and permission arrays with the existing JSON object. Keep unrelated settings and restrictions. Do not erase existing rules to match an empty example array.

JSON does not allow comments or trailing commas. Restart the interface after editing and check its active permissions. Compare the samples in workshop-content/01-codex-workspace/samples/cursor/ with your files before merging.

5: Verify the local runtime

In your OS terminal or the terminal of your selected desktop app, return to the repository root. Use your existing Ansible environment and run:

# Enter Lab 1 so Ansible uses its local configuration and inventory.
cd workshop-content/01-codex-workspace
# Check the sample playbook syntax without running its tasks.
ansible-playbook --syntax-check playbooks/hello.yml
# Run the sample checks on localhost using your existing Ansible installation.
ansible-playbook playbooks/hello.yml

If ansible-lint is already installed, you can also run ansible-lint playbooks/hello.yml.

The sample targets only localhost, prints the host OS, Ansible version, and Python executable, and verifies Linux or macOS. It does not contact managed nodes or change host configuration.

Use this first prompt in either Codex or Cursor with the repository open:

Read README.adoc and workshop-content/02-shell-to-ansible/README.adoc.
Explain the workshop structure and prerequisites for converting the legacy
Python NetBox installer to Ansible. My RHEL or macOS workstation is the control
host. Explain the installer's managed-host requirements.
Use my existing working Ansible installation for validation. If its environment
is unavailable, report the missing command and ask for the environment details.
Keep this task to inspection and explanation, and do not connect to managed hosts.

6: Setup checklist and troubleshooting

Check

Success criteria

Selected AI tool

Your chosen Codex or Cursor interface signs in with the approved account and opens the checkout

Installation choice

One tool and one interface are sufficient; checks for the other paths are optional

Existing Ansible installation

ansible-playbook --version succeeds in the terminal used by your selected tool

Local verification

Syntax check and the sample playbook pass on localhost; lint is optional

  • If Ansible is missing or fails, restore your existing installation or ask the instructor for help.

  • If your AI tool cannot find Ansible, use the activation command or absolute executable path from section 1.

  • If Codex shell networking is blocked, inspect the active policy. Use -c 'sandbox_workspace_write.network_access=true' for one session when the task needs it and your organization’s policy permits it.

  • If the Linux sandbox fails, check bwrap --version and host namespace restrictions with the instructor. Keep SELinux enabled.

  • If the RHEL desktop RPM fails to install or launch, use Codex CLI and save the error for troubleshooting.

  • If Cursor sign-in fails, check that you used the account approved for the workshop.
