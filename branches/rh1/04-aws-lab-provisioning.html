Lab 04: Customer NetBox delivery project

With your assigned team, migrate the Python installer to Ansible for a fictional customer. Deploy NetBox on AWS, add demo hosts in its UI, and query them with Ansible dynamic inventory.

The customer

Switchboard Supply has depended on the Lab 2 installer for years. The people named in its comments have moved teams, the deployment instructions are incomplete, and nobody wants to be the next person to run it by hand. The company also manages AWS networks and keeps copying host addresses into static inventories.

The customer wants Ansible to deploy NetBox and use its host records as inventory. Your team must show a working deployment and a second run that preserves credentials and release state. Leave instructions another team can follow. Use workshop-content/04-aws-lab-provisioning/customer-brief.adoc as your project brief.

Work with your assigned team. Choose your architecture and division of work together. Write your own prompts and choose models based on your Lab 3 results. Agree on what you will deliver and explain any unfinished work to the customer.

Deliverables

  • Ansible content that installs and configures NetBox and its dependencies, based on the Python installer from Lab 2.

  • AWS hosts running NetBox, with a documented network layout and deployment instructions.

  • Manually created NetBox host records and a working demo that queries them through netbox.netbox.nb_inventory.

  • A customer handover with validation evidence, operating instructions, known limitations, and cleanup steps.

The final demo must execute an Ansible play against team-owned AWS hosts selected from NetBox. Show the host records in NetBox and the inventory returned by the plugin.

Before you start

Complete Labs 1 through 3. Bring your own AWS environment that your team is authorized to use for testing and deployment. Confirm the account, region, allowed services, IAM permissions, budget, and cleanup owner together. Use your existing RHEL or macOS Ansible control workstation and an approved AI tool.

You need access to EC2 and the networking resources your design requires. Use the community NetBox installation based on the Lab 2 script. Your team will enter its demo hosts in the NetBox UI after deployment.

Step 1: Organize the team

Create a team branch and a project directory. Replace switchboard with your team name:

# Create a branch for the team's delivery work.
git switch -c team/switchboard-netbox
# Create a directory for the project and its customer handover.
mkdir -p workshop-content/04-aws-lab-provisioning/teams/switchboard

Agree on variable names and who will edit each file before working in parallel. Divide responsibilities such as the installer migration, AWS infrastructure, NetBox host records, inventory demo, and review. Pair or rotate tasks so each student can explain part of the project. Ask a teammate or another team to act as the customer during scope review and the final demo. Review each other’s changes and resolve conflicting assumptions in the code and README.

Review your ports from Labs 2 and 3. Choose a port to finish, or start again if none meets your needs. Use your model comparison notes to decide which requests need more reasoning effort. Use the customer brief to decide what to ask the tool.

Step 2: Agree on an architecture and acceptance plan

Sketch the AWS hosts, subnets, access paths, and NetBox services. Decide whether to keep the installer’s services on one host or split application, PostgreSQL, and Valkey roles. Choose a supported OS and compatible dependency versions. If you change the source’s OS assumptions, document and test those changes.

Tip

Consider t3.small instances for demo targets or separate services with low demand. They have 2 vCPUs and 2 GiB of memory. Measure memory use before choosing one for NetBox. For an all-in-one community NetBox host, consider a larger instance such as t3.medium and measure memory during installation and the demo. Check regional availability, CPU credit behavior, and storage before launching. See AWS instance specifications.

Use instance roles or your organization’s approved temporary credentials. Restrict administrative access to the team’s approved network or access service. Keep PostgreSQL and Valkey private. Decide how you will configure HTTPS and manage certificates for the NetBox endpoint. Tag team resources so you can identify ownership and clean them up without affecting shared infrastructure.

Choose how to create the AWS hosts. Try Ansible provisioning, or document the existing approved infrastructure you use. Use Ansible for the NetBox installation and configuration. Document which playbook deploys NetBox. Use a separate bootstrap inventory until the NetBox API is available.

Write your checks before generating more code. Test installation and a second run, including saved credentials, release state, service health, and web access. Also check manual host entry, dynamic inventory, and cleanup.

Step 3: Finish the Ansible migration

Compare your migration with the installer and workshop-content/02-shell-to-ansible/migration-checklist.adoc. Convert the installer stages to Ansible tasks. Running the original script from a playbook does not complete the migration.

Group related tasks into roles or task files. Use fully qualified module names, variable defaults, templates, and handlers. Declare collection dependencies and supported versions. Use shell or command tasks only where a suitable module is unavailable. Document how they detect changes and behave on reruns. Protect secrets with approved secret storage or Ansible Vault, restrictive file permissions, and no_log where required. Keep secrets out of prompts, committed examples, and demo evidence.

Preserve generated secrets and the selected release across reruns. Explain any intentional changes to the installer’s state file, refusal conditions, wildcard allowed-hosts default, TLS behavior, or unconditional restarts. Document the supported upgrade and recovery procedures, including what you have not tested.

Review the generated changes before running them. Run syntax checks and your available lint tools, then deploy to the agreed AWS hosts. Save the results of your service, login, and API checks. Run the deployment again and investigate changes that should not repeat. Document necessary exceptions, such as explicit migration tasks.

Step 4: Manually add demo hosts to NetBox

Choose team-owned AWS hosts for the inventory demo. Use their actual names and addresses. Confirm how your control workstation will reach them.

Add the records through the NetBox UI:

  1. Create any supporting records your chosen host type requires, such as a site or cluster.

  2. Create a virtual-machine or device record for each demo host and set its status to active.

  3. Add an interface to each host.

  4. Create an IP address with its prefix length and assign it to that host’s interface.

  5. Set the address as the host’s primary IPv4 or IPv6 address.

  6. Add the same team-specific tag to each demo host so your inventory can select them.

Check each host’s name, primary IP, status, and tag in NetBox before querying the inventory. Document these manual steps in the customer handover so another operator can add a host.

Step 5: Query the NetBox dynamic inventory

Use netbox.netbox.nb_inventory for the final inventory source. Read its inventory plugin documentation and install the required collection and Python dependencies. Keep the API endpoint and token in your environment or approved credential store. Use a read-only inventory token for the queries. Keep certificate validation enabled and document any private CA trust configuration. Filter the inventory to the team’s demo tag and hosts with primary addresses. Choose addresses reachable from your control workstation, or configure an approved connection path.

Document the inventory filename, group selection, connection user, and credentials required for the demo. You may use AWS discovery or a static inventory to deploy NetBox. Use NetBox to select hosts for the final customer demo.

Adapt these commands to your project from its directory:

# Query NetBox and display only the groups selected by your inventory configuration.
ansible-inventory -i inventory/netbox.yml --graph
# Test Ansible connectivity to the hosts selected from NetBox.
ansible netbox_demo -i inventory/netbox.yml -m ansible.builtin.ping
# Run the team's demo playbook against the same NetBox inventory.
ansible-playbook -i inventory/netbox.yml demo.yml

Create the inventory configuration, netbox_demo group, and playbook, or adapt the commands to your project layout.

Change a demo host’s tag or another field your inventory filters use. Refresh the inventory and show that host selection changed without editing a static host list. Restore the record afterward. Account for inventory caching in your refresh procedure.

Step 6: Present the customer demo

Present the original problem and explain what the customer can now do with Ansible. Use workshop-content/04-aws-lab-provisioning/customer-demo-checklist.adoc to prepare evidence.

Demonstrate the deployed NetBox service and explain the Ansible content that configured it. Show a second deployment run and describe any remaining changes. Show the hosts your team manually entered in NetBox, including their interfaces, primary IPs, and team tag. Query the NetBox inventory and run your demo playbook against the selected AWS hosts. Show the inventory membership change and explain how the customer would add another host in NetBox.

Explain what you tested and what remains incomplete. List the work needed before production use. Give the customer a README with dependency versions and required permissions. Include instructions for deployment, reruns, verification, manual host entry, inventory queries, recovery, and teardown. Include your architecture decisions and useful AI model comparison findings.

Step 7: Handover and cleanup

Review the staged files for credentials and private output before committing your team’s work. Agree on how to share the branch or pull request with the customer. Keep the source, test results with secrets removed, and operating instructions together.

Use your documented teardown process after the demo, unless the environment owner explicitly wants the resources retained. Remove only team-owned resources. Account for instances, volumes, public addresses, and network resources. Check AWS to confirm cleanup. Record any retained resources, their owner, and when they should be removed.

Completion checklist

  • The team has reviewed Ansible content that installs and configures NetBox.

  • NetBox infrastructure is running on the team’s AWS hosts, with installation and rerun evidence.

  • The team manually added demo host records, interfaces, primary addresses, and a team tag in NetBox.

  • The customer demo queries NetBox dynamic inventory and runs Ansible against the selected AWS hosts.

  • Inventory membership changes when the team changes a NetBox record.

  • The handover explains limitations, operating procedures, and cleanup, with no committed secrets.
