=== Understanding the Basic Template Directory Structure

----

├── <lab-module>.                    # Lab Module Directory
│   └── <content>                    # Associated content for the lab
./documentation/modules/ROOT/
├── assets
│   └── images                       # Images used in your content
│       └── <lab-module>             # Lab Module Directory
│           └── example-image.png    # Images
├── nav.adoc                         # Navigation for your lab
├── pages                            # Your content goes here
│   ├── index.adoc                   # First page of your lab, e.g. overview etc
│   └── <lab-module>                 # Lab Module Directory
│       └── 01-lab-1.adoc            # Lab 1 content
└── partials                         # You can add partials here, reusable content inserted inline into your modules
    └── example_partial.adoc
----

=== Using Containers (Recommended)

In order to test and develop on your local machine, you can use a specially built container with Podman or Docker as follows.

. Clone this repo and `cd` into it
. Commit your content to git before previewing — Antora only indexes committed files when using the local content source (`url: .` in `default-site.yml`)
. When you make changes to the content, all you need is to kill the container and run it again.
+
[source,sh]
----
podman run --rm --name antora -v $PWD:/antora -p 8080:8080 -i -t ghcr.io/juliaaano/antora-viewer
----

For SELinux environments, `:z` may need to be appended to the volume mount:

----
podman run --rm --name antora -v $PWD:/antora:z -p 8080:8080 -i -t ghcr.io/juliaaano/antora-viewer
----

Live-reload is not supported.

=== Preview from GitHub

The *Workshop preview and Pages* workflow publishes `main` at the site root:

https://redhat-services-platform-team.github.io/ansible-amers-ai-workshop/

Each pull request from a branch in this repository gets a separate preview, updated when commits are pushed:

https://redhat-services-platform-team.github.io/ansible-amers-ai-workshop/previews/pr-3/

Replace `3` with the pull request number.
The deployment link in the workflow run and the pull request's deployment activity points to that preview.
Antora builds the preview with its own base URL so navigation, assets, and canonical links stay within it.
Closing or merging a pull request removes its preview; other previews remain available.
Automatic preview publishing and cleanup take effect once this workflow is merged into `main`.

To publish an unmerged branch manually, open *Actions → Workshop preview and Pages → Run workflow*:

. Select the branch.
. Check *publish*.
. Enter its open pull request number in *pr_number*.

Manual publishing from `main` refreshes the root without replacing previews.
Leave *publish* unchecked to build downloadable artifacts only.
Fork pull requests build artifacts but do not publish or receive repository write credentials.

The workflow saves the combined generated site on the `gh-pages` branch, preserving other previews between runs.
It rebuilds the root from `main` during every publishing run.
Keep *Settings → Pages → Build and deployment → Source* set to *GitHub Actions*, not branch publishing.
The `github-pages` environment must allow deployments from the preview branches.
A repository administrator can select *Settings → Environments → github-pages → Deployment branches and tags → No restriction*.
See https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages[GitHub's custom workflow documentation].

Download `workshop-main` or `workshop-preview` from the workflow run's Artifacts section to inspect a generated build.
Hosted builds contain their published base URL; use the hosted preview to verify navigation.
For a local preview with local links, use the build utilities above.

== Instructor AWS Git environment

Use link:instructor_automation/README.md[instructor_automation] to provision one RHEL 9 Gitea server in an AWS account.
Supply a team dictionary to create private organizations, permission groups, and local student users.
The playbook discovers the public Route 53 zone, deploys a `t3.medium`, and uses AWS EC2 dynamic inventory to find the host.
It saves the Git URL, organization URLs, and initial passwords in a private access sheet.
Start with discovery mode to check the account keys and DNS name before provisioning.
